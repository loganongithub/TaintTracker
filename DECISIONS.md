# Decisions

One line per decision, with the reason. Newest at the bottom.

- 2026-11-13: Bug classes are SSRF and path traversal. A second bug class is mostly another sink list, so two is cheap.
- 2026-11-13: Flask only; FastAPI is a stretch goal after phase 4. FastAPI input arrives as typed function parameters, which needs a different source model.
- 2026-11-13: When unsure, flag. Findings are triaged by hand and the phase 5 ranking step sorts out the noise.
- 2026-11-13: `engine/` never imports from the plumbing. Keeps the engine testable on a plain string of source code.
- 2026-11-13: Phase 5 starts at 100 repos and scales to thousands before triage. 100 is enough to debug the pipeline; more repos raises the odds of real findings.
- 2026-11-13: Track the benchmark false-positive rate from phase 4 onward. The phase 5 ranking step needs something to tune against.
- 2026-11-13: Target is triaging real findings by about April 2027. Applications open around July 2027 and maintainers can take one to three months to respond.
- 2026-11-13: Each test snippet declares its expected result in a first-line `# expect:` comment. The expectation sits next to the code, with no separate file to keep in sync.
- 2026-11-13: The engine's whole public surface is `analyze(source, filename) -> list[Finding]`. One function is enough for the CLI and the tests, and it can be built on in phase 3.
- 2026-11-13: Docker is deferred until phase 5. It is not installed and nothing before the repo scan needs it.
- 2026-11-13: Claude writes the engine, reversing the original "I write it myself" rule. Logan's call, to get building faster; Logan still has to be able to explain every part of it.
- 2026-11-13: A taint value is the set of bug classes a value is still dangerous for, not a yes/no flag. Sanitizers are bug-class specific: `secure_filename` fixes path traversal but not SSRF.
- 2026-11-13: Sinks are argument-specific (`requests.get` checks only `url`). Tainted data in `timeout=` is not SSRF, and this removes a whole family of false positives.
- 2026-11-13: `int()`, `float()`, `bool()` and `len()` return clean values. Their output cannot carry a hostname or `../`.
- 2026-11-13: A call is tainted if any argument or the object it is called on is tainted. Covers `url.strip()`; over-taints some harmless calls, which fits "flag when unsure".
- 2026-11-13: Response bodies are not a separate source, but `requests.get(tainted)` returns tainted data through the call rule. Deliberate: second-order flows come for free.
- 2026-11-13: After an `if`, a variable is tainted if either branch taints it; loop bodies run twice. Simple, never misses a flow through a branch, and needs no control-flow graph.
- 2026-11-13: A constant prefix `http(s)://host/` clears SSRF taint; a prefix with no slash after the host does not. Without the slash, `@evil.com` or `.evil.com` can still change the host.
- 2026-11-13: Route parameters with `int`, `float` or `uuid` converters are not sources; default and `path` converters are. Both of those are flagged even though the default converter blocks `/`, because backslashes still traverse on Windows.
- 2026-11-13: Names are resolved through the file's imports before matching rules. `import requests as http` and `from flask import request as req` must still match.
- 2026-11-13: Cross-function tracking uses per-function summaries, not inlining callees at each call site. Each function is analyzed without knowing its callers, which scales to large repos and handles recursion.
- 2026-11-13: Summaries are built by giving each parameter a label naming itself and seeing where the label ends up. The same tracker code produces both real findings and summaries, so there is one set of propagation rules.
- 2026-11-13: Summaries are recomputed in rounds until none change (capped at 10). Functions call each other in any order, including recursively; taint only grows, so the loop must stop.
- 2026-11-13: A call into a project function uses its summary instead of the "any tainted argument" rule. A helper that sanitizes or ignores its argument stops producing false positives.
- 2026-11-13: A cross-function finding is reported at the sink line, with the calling handler in the message. The sink is where the fix goes; the message keeps the entry point for triage.
- 2026-11-13: A helper whose parameter reaches a sink is not a finding on its own, only when a caller passes it tainted data. Otherwise every wrapper around `open` or `requests.get` would be flagged.
- 2026-11-13: Imported names are matched to project functions by dotted suffix, and re-exports through `__init__.py` are followed. Repos often have their import root below the scan root (`src/pkg/...`).
- 2026-11-13: Only top-level functions can be called across functions; `self.method()` calls and class instances are not resolved. That needs type inference; revisit only if the CVE benchmark shows misses from it.
- 2026-11-13: Benchmark cases pin exact commits; the vulnerable version is the parent of the fix commit. Results are reproducible and each case needs only one hash.
- 2026-11-13: A CVE counts as detected on a file-level match (right bug class in one of the CVE's files). Line numbers are not in advisories; each detection still needs a manual check that it is the same bug.
- 2026-11-13: The false-positive rate is computed only over findings labelled by hand in `benchmarks/labels.toml`; unlabelled findings are reported separately. Calling every non-CVE finding a false positive would be wrong, since some are real bugs.
- 2026-11-13: The benchmark starts with 8 CVEs in 5 repos and grows from the CVE-2022-315xx `send_file` batch. Small enough to verify every entry by hand first.
- 2026-11-13: Benchmark checkouts are shallow, git-ignored, and only read, never executed. Keeps downloads small and third-party code out of the repo and off the CPU.
- 2026-11-13: `safe_join` (Flask and Werkzeug) is a path-traversal sanitizer. The benchmark showed it is the standard fix: two of four fixed versions were still flagged without it.
- 2026-11-13: Rules are only added from the benchmark when they are general library facts, never to make one case pass. Tuning to 8 CVEs would inflate the score and not carry over to the real scan.
- 2026-11-13: Method calls are still not followed after the first benchmark run, even though that caused both misses (Whoogle's `g.user_request.send`). The fix is a design choice with a false-positive cost, to be decided before phase 5.
- 2026-11-13: Reversed the line above: `obj.method()` is matched to a project method when exactly one class defines that name. Real type inference is out of scope; on the benchmark this caught both Whoogle SSRFs and added no other findings across the five repos.
- 2026-11-13: A guessed method match can only add taint to the usual "tainted in, tainted out" result, never remove it. The guess may be the wrong class, and a wrong guess must not hide a real flow.
- 2026-11-13: Method names that built-in types also have (`get`, `read`, `update`, ...) are never guessed, and neither are calls on a name bound by `import x`. `d.get(k)` is almost always a dict, and `os.path.join` is a module function.
- 2026-11-13: `self.method()` resolves to the enclosing class's own method and is trusted fully. That one is not a guess (ignoring subclass overrides).
- 2026-11-13: One finding per sink line, even when several handlers reach it. Whoogle's two SSRF CVEs share one sink and show as one finding naming only the first handler; listing every entry point is deferred to phase 6 triage support.
- 2026-11-13: Route strings written as `"a" + "b"` are read as one literal. Labelling showed a concatenated opendiamond route made every parameter tainted, including `<int:...>` ones; fixing it removed two false positives.
- 2026-11-13: A benchmark finding is labelled "fp" when it is not a vulnerability, even if the data flow is real (for example an admin-only folder picker). The rate should predict how much triage time is wasted, not how often the engine's reasoning is wrong.
- 2026-11-13: The true-positive count uses distinct findings, not one per CVE. Two CVEs can share a finding, and counting it twice flattered the false-positive rate.
- 2026-11-13: Database lookups keyed by tainted ids stay tainted for now, although they caused 6 of 13 labelled false positives. Treating `get_book(id)` results as clean needs a rule for "lookup by id" that is not just a name list; revisit with the larger benchmark.
- 2026-11-13: The benchmark is split into a "tuned" set and a "heldout" set, reported separately. The first 8 CVEs shaped the rules, so only cases added afterwards give an honest detection rate.
- 2026-11-13: Never-fixed CVEs are pinned at the repository's head commit and matched at repository level. There is no fix commit to say which files matter; the looser match is marked in the results and still needs a manual check.
- 2026-11-13: The held-out set is 9 cases, not the 15 to 20 planned. About half the CVE ids in the batch have no OSV record, and repos that were deleted, very large, or changed since the CVE were left out.
- 2026-11-13: Dropped the repository-level match after one run and gave every case a `files` list. It credited dls with a detection from unrelated findings while the real vulnerable file had been skipped.
- 2026-11-13: The false-positive rate counts only findings a person has read and labelled, including CVE-credited ones. Assuming every finding in a CVE's file is true produced a flattering 17% where the labelled figure is 43%.
- 2026-11-13: "Cleared by fix" compares finding counts and has a "partly" value. Fix commits often fix one of several flagged places in a file, and line numbers shift, so a yes/no file match hid real clears.
- 2026-11-13: Python 2 files are skipped, not converted. Both held-out misses (dls, SetupBox) are Python 2 files that Python 3's `ast` cannot parse; `lib2to3` is gone from current Python, and Python 2 apps are a shrinking target.
- 2026-11-13: No engine rule was changed in response to the held-out results. That is what keeps the held-out number honest.
- 2026-11-13: Taint has two strengths. Weak taint means the attacker only chose which stored value is used (`db.get_book(id)`, `table[key]`); it gives a low-confidence finding. This replaces the earlier "database lookups stay tainted" line: 6 of 13 labelled false positives came from lookups.
- 2026-11-13: Low-confidence findings are kept, not deleted, and hidden by default (`taintscan scan --low` shows them). "Flag when unsure" still holds, and the ranking step can use confidence as a signal.
- 2026-11-13: An unknown method call keeps its arguments' content only for string and path methods, library calls, and methods on a tainted value; a method on a project object or local variable weakens it. This is how lookups are told apart without a list of method names.
- 2026-11-13: A tainted object passed as `self` is weak inside the method. The engine does not track fields, so `self.output_dir` on an object built from request data is usually not the attacker's part; csm's report writers showed this.
- 2026-11-13: Three kinds of validation check are understood: membership in a collection the attacker does not control, `re.match`/`fullmatch`, and `startswith` on a path that came from `realpath`/`abspath`/`normpath`. These cover the common fixes; anything else (blocklists, custom validators) is deliberately not trusted.
- 2026-11-13: A check only counts when it is sound: `a or b` must both fail, `a and b` must both hold. Calibre-Web's `ext not in ALLOWED and '' not in ALLOWED` is therefore not trusted, because it lets everything through when the list contains ''.
- 2026-11-13: A host allowlist check clears the URL the host was parsed from, for SSRF only; a scheme check clears nothing. Checking `urlparse(url).hostname` is the standard SSRF fix, while the scheme says nothing about where the request goes.
- 2026-11-13: A branch that always returns, raises or aborts does not flow into the code after the `if`. Needed for validation checks, and it removes taint that could never reach the later code.
- 2026-11-13: Variables assigned from a constructor remember their class (`s = requests.Session()`, `repo = Repo()`), as do module-level objects, and methods are looked up through base classes. Replaces guessing by name where the type is visible; the guess remains as a fallback.
- 2026-11-13: `os.makedirs` was added as a sink and removed again the same day. It produced six findings on the benchmark for a low-impact operation (creating a directory).
- 2026-11-13: New sinks: `requests.Session` and `httpx.Client` methods, `urllib3.PoolManager.request`, `codecs.open`, `shutil.copy`/`copyfile`/`move` (source argument), `send_from_directory` (directory argument), and `read_text`/`write_text`/`read_bytes`/`write_bytes` on a tainted path object.
- 2026-11-14: Commits carry no Claude co-author line. Logan's call: GitHub should list Logan as the only contributor.
- 2026-11-14: Findings and repo metadata go in one SQLite file (`data/taintscan.db`). No server to run, it is in the standard library, and ranking can be a SQL query.
- 2026-11-14: Repos are found with GitHub's repository search, not code search. It needs no token for small runs and returns stars, size and last push, which ranking needs.
- 2026-11-14: The default search is Python repos mentioning "flask", 20 to 3000 stars, pushed in the last two years, under 50 MB, sorted by most recently updated. Enough stars to matter, few enough to be under-audited, and active enough that a maintainer may answer.
- 2026-11-14: Clones are shallow and deleted after each scan; the scanned commit hash is stored. Disk use stays flat however many repos are scanned, and triage can fetch the exact code again.
- 2026-11-14: Repos with more than 3000 Python files are skipped. They are rarely single Flask apps and would dominate the run time.
- 2026-11-14: Docker is not used for the scan. Scanned code is only parsed, never run, so there is nothing to sandbox. Replaces the earlier "Docker is deferred until phase 5" line.
- 2026-11-14: `io.BytesIO` and `io.StringIO` clear path-traversal taint. The first 100-repo scan flagged `send_file(io.BytesIO(data))`, which reads no file.
- 2026-11-14: Custom validator functions (`validate_outbound_url`, `path_is_child_of`) stay untrusted in the engine and become a ranking signal instead. They caused most false positives in the first spot-check, but trusting any function with "validate" in its name would hide real bugs.
- 2026-11-14: Repos that fail to clone on Windows (file names NTFS rejects) are recorded as errors and skipped. It was 1 of 100; not worth weakening git's path protection.
- 2026-11-14: Ranking is a separate step that orders findings; it never removes one. The engine keeps flagging when unsure, and a person can always read further down the list.
- 2026-11-14: The score is a sum of hand-set adjustments, each stored with its reason (`taintscan top --why`). A score has to be explainable in triage and in an interview; a learned model would need far more labels than the 24 that exist.
- 2026-11-14: A finding lists every entry point and is scored by its most dangerous one. Replaces "one finding per sink line, naming only one handler": a sink behind one admin view and one public view is a public bug.
- 2026-11-14: Source labels record where the data came from (`request`, `<path:x>`, plain `<x>`). A plain URL parameter cannot contain "/", which makes most path-traversal findings from it unexploitable on Linux, so it is the strongest cheap signal.
- 2026-11-14: Login and admin decorators lower the score but are judged only from decorator names. Good enough for ordering; whether the check really protects the route is a triage question.
- 2026-11-14: A call to a validator-looking function (`validate_*`, `*safe*`, `is_child*`, ...) on the path lowers the score by 20 but never clears taint. Solara and TimeTracker showed such checks are usually real, but trusting names in the engine would hide the cases where they are not.
- 2026-11-14: Repos with more than 30 or 100 findings are penalised. Two of the first 100 repos produced 410 of 526 findings; both are tools where file access is the feature.
- 2026-11-14: Ranking quality is measured as AUC over the hand-labelled benchmark findings, without repo signals. It gives the weights something to be tuned against; the first value was 0.87 on 24 findings, which is too few to tune on yet.
- 2026-11-14: `taintscan top` shows at most three findings per repository by default. Triage time is better spent across repositories than down one.
- 2026-11-14: Rescans reuse kept clones (`scan-all --rescan --keep`). Engine and ranking changes should not cost another 1 GB download each time.
- 2026-11-14: A tainted value appended to an untainted, non-literal prefix (`BASE_URL + path`, `f"{config['URL']}/x/{name}"`) is weak for SSRF. The attacker most likely controls only the path; top-ranked findings in anx-calibre-manager and metabrainz.org were this shape. A prefix ending in `//` or `@` keeps it strong, because what follows is still the host.
- 2026-11-14: The counter in `for i, x in enumerate(items)` is never tainted. A top-ranked finding in pick-a-recipe was a file named from the loop counter.
- 2026-11-14: Calling a helper that itself calls a validator-looking function marks the caller as guarded, for ranking only. Validation often lives one call away from the sink.
- 2026-11-14: A failed clone removes its folder. Git can leave a half-checked-out tree, which the kept-clone shortcut then scanned as if it were complete.
- 2026-11-14: Stopped adjusting rules against the 100-repo top 20 after four changes. Each fix was a general rule, but tuning to one list of twenty is the same trap as tuning to the benchmark; the next evidence should come from a larger scan and hand triage.
- 2026-11-15: False-positive causes were found by reading 36 findings sampled across the 100-repo scan, one or two per repository, not by guessing. Rules that come from real code are less likely to be wrong than rules that come from imagination.
- 2026-11-15: A countermeasure downgrades to low confidence unless the engine can actually see why the code is safe; only then does it clear. Downgraded findings stay in the database and in `scan --low`, so a wrong rule costs rank, not visibility.
- 2026-11-15: Every countermeasure has a paired test: the safe pattern and a look-alike that is still vulnerable and must stay high-confidence. This is the guard against a rule that hides real bugs.
- 2026-11-15: A `Request(url, data=...)` object carries only its URL's taint. A tainted body sent to a fixed host is not SSRF.
- 2026-11-15: The reply to an HTTP call is strongly tainted only if the URL was; a tainted body or header makes it weak. A fixed host's reply is not attacker-controlled content, even when it echoes some of it.
- 2026-11-15: Temp-file paths (`tempfile.*`) are weak for path traversal, not clean. The OS picks most of the path, but a tainted `prefix` or `dir` still ends up in it; I first made them clean and reversed that after a spot-check.
- 2026-11-15: `Path(x).name`, `.stem` and `.suffix` clear path traversal. They are the last path component, the pathlib spelling of `basename`.
- 2026-11-15: Module-level string constants are read as text, including across imports. `API_URL + path` and `TEMPLATE.format(x)` pin the host exactly as a literal would.
- 2026-11-15: `a, b = f()` binds each name to its own position when every `return` in `f` gives a tuple of that length. Without it `output, filename = build()` smeared the tainted filename onto the in-memory buffer.
- 2026-11-15: Guessing a method by name ignores classes defined in test code. A mock `save()` in a test suite was matched to every `upload.save(...)` in the application.
- 2026-11-15: `.save(path)` on a tainted object is a path-traversal sink. It replaces the accidental mock finding with the real one: an upload written to an attacker-chosen path.
- 2026-11-15: `record.id` and `record.pk` are weak. They hold a database key, not the content the object was built from.
- 2026-11-15: A function whose name claims safety for paths or URLs (`is_safe_path`, `validate_outbound_url`, `path_is_child_of`, `sanitize_*`) weakens what it checks or returns. Revises "custom validators stay untrusted": they are still never cleared, but name plus use as a guard is enough evidence to lower confidence.
- 2026-11-15: That name list deliberately leaves out "allowed" and bare "valid", and anything with load/dump/eval in it. `allowed_file(name)` checks an extension and says nothing about `../`; `yaml.safe_load` returns attacker content.
- 2026-11-15: Testing a value for `/`, `\` or `..` before use weakens it for path traversal. It is a partial check (bepasty tests only for `/`), so weak, not clear.
- 2026-11-15: After the first round, a function is analyzed again only if something it calls changed. Scanning the 100 repos fell from over ten minutes to under two; the result is the same because a summary depends only on the function's code and its callees' summaries.
- 2026-11-15: Three known false positives are left alone: a validator inside a nested function (EasyNas) and a hand-rolled `allowed` flag (docsight). Fixing them needs nested-function summaries and boolean reasoning, which is more machinery than three findings justify.
- 2026-11-15: Triage verdicts live in `data/labels.toml`, which is git-ignored. They name possible vulnerabilities in other people's projects that are neither confirmed nor disclosed, so they must not reach the public repo.
- 2026-11-15: Verdicts are "real", "plausible", "unsure" or "fp", and "real" is reserved for a bug confirmed by running the app locally. Reading code can show a flow looks exploitable; it cannot show that it is.
- 2026-11-15: Static triage was done by Claude; nothing was run. Running a stranger's application is executing untrusted code, which Logan should choose to do, in a sandbox, per finding.
- 2026-11-15: `taintscan top` shows each finding's verdict and a tally. The share of the top 20 that is plausible or real is the project's headline measure.
- 2026-11-15: Functions nested in another function can be called by name from their siblings and their parent. App factories (`def create_app(): ...`) define views and helpers this way; without it a validating helper was invisible, and so was a vulnerable one.
- 2026-11-15: `resolved.is_relative_to(base)` is a path check the engine understands, like `startswith` on a resolved path. It is the pathlib form of the same validation.
- 2026-11-15: `re.sub(r"[^...]", "", x)` clears path traversal when the kept characters do not include "/". Stripping to a safe alphabet is a common and sound sanitizer; one that keeps "/" is not.
- 2026-11-15: A view with no login decorator in an app that has a `before_request` hook gets auth "hook" and loses the "+10 no login" bonus. Three of the top-20 apps enforce login in such a hook; the engine cannot tell which routes it covers, so it neither rewards nor penalises.
- 2026-11-15: A function that resolves a path and has an `if` that raises or returns nothing counts as guarded for ranking, whatever it is called. Validators are not always named in English (`_ziel_pruefen`).
- 2026-11-15: The slow rescan was disk wait, not the engine: about two minutes of CPU in eleven of wall time. No code change; first-time reads of 1.4 GB of clones are slow on this machine.
- 2026-11-15: Taint that starts in the middle of a path component (`"report_" + x`, `f"{date}_{x}.json"`) is weak for path traversal. Escaping then needs a directory named `report_..` to exist, so it only works on Windows; two top-20 findings were this shape.
- 2026-11-15: Taint at the start of a component (`dir + "/" + x + "_report"`) stays strong. That is the exploitable case, and the paired test pins the difference.
- 2026-11-15: When a lookup on a project object returns something (`job = JobStore.get_by_id(job_id)`, then `if job is None: return`), the key is weak afterwards. It names a record that exists. `os.path.isdir(path)` does not count: a path that exists is not a path that was checked.
- 2026-11-15: Regex checks on `x or ""` count as checks on `x`. Real code guards against `None` this way before matching.
- 2026-11-15: Ranking: a plain URL parameter now costs 25 (was 15) for path traversal and test code 40 (was 30). After two triage rounds, neither kind had produced a plausible finding, and both were still reaching the top 20.
- 2026-11-15: The "not really a safety function" exclusions are now exact (`safe_load`, `safe_dump`, `safe_substitute`, `mark_safe`, ...) instead of loose substrings. The loose pattern `safe_str` matched `_is_safe_stream_url`, so a real SSRF guard was being ignored; triage caught it.
- 2026-11-15: Left alone after round three: ids proved against a stored list by hand-written comparison, and "issued by this server" token checks. Each appeared once; a rule per one-off is how an engine gets fitted to its sample.
- 2026-11-13: (Superseded later the same day, see the validation-check lines above.) Allowlist checks (`if host not in ALLOWED: abort()`) are not recognised as sanitizers yet. Needs reasoning about conditions; revisit when the CVE benchmark shows how often it matters.
